# 7B 모델이 모르는 것은 코드와 데이터에 두었다: ONVIF 표준 RAG

**정원석** | 2026.06~10 (표준 조사 6월~, RAG 구축 10월) · 회사 프로젝트 · 로컬 RAG · qwen2.5:7b · e5-large + bge-reranker-v2-m3 · Qdrant · RTX 4070 SUPER 12GB

> 카메라·엣지 AI 장비 개발자가 "이 기능을 ONVIF에 맞게 넣으려면?"이라고 물으면, 표준 원문을 근거로 답하는 사내 챗봇.
> 조건은 **로컬, 7B, GPU 12GB.** 그래서 모델이 모르는 지식은 모델에게 맡기지 않고 **데이터와 코드로 옮겼다.**

<sub>점수는 모두 작성자가 만든 소규모 평가셋(9~39문항) 기준이다. 팀 실사용 검증은 하지 못했다.</sub>

---

**1. 큰 모델을 쓸 수 없었다.**
표준 원문(docbook·XSD·WSDL, Profile PDF)은 방대한데, 답변 모델은 로컬 7B로 정해져 있었다. 외부 API와 더 큰 모델은 쓰지 않기로 한 결정 사항이었다.
<sub>스펙은 26.06 릴리즈로 고정, 색인 4,248조각. GPU 12GB에 임베더·재정렬 모델(약 2.5GB)과 LLM(16k 컨텍스트, 약 5.5GB)이 함께 올라가 거의 가득 찬다.</sub>

**2. 원문은 코드로 뽑아 그대로 보여 주고, 7B에게는 보조 설명만 맡겼다.**
표준 기능을 묻는 질문에는 원문의 operation·이벤트·분석 규칙 표를 **LLM 없이** 그대로 보여 준다. 7B가 쓴 문장은 "참고 설명 (7B 작성 — 위와 다르면 위를 따르세요)"으로 따로 표시했다.
<sub>원문에서 자동 추출: operation 575개, 이벤트 127개, 분석 규칙 17종의 토픽·파라미터·요구 수준. 사람이 만든 것은 업무 표현 → 표준 기능 연결표 48항목뿐이고, 빌드할 때 원문 절이 실제로 있는지 검증한다.</sub>

**3. 질문 유형마다 길을 나눴다.**
조회, 기능 추가, Profile 질문을 먼저 가르고, 질문 속에 규칙·타입·operation 이름 같은 식별자가 있으면 그것이 연결 대상을 먼저 정하게 했다. "이 요소는 어느 요소 아래에 넣어?" 같은 스키마 질문은 XSD 구조를 코드로 판정한다.
<sub>식별자 우선 연결을 넣은 뒤 경로 일치가 dev 29 → 32/37, holdout 23 → 31/39. 순서 질문은 XSD 모델 그룹(sequence/all/choice)으로, 소속 질문은 스키마 인덱스로 판정.</sub>

**4. 9문항 충족률 0.074에서 0.894까지.**
원문 체크리스트 기준 충족률이 0.074 → 0.395 → 0.467 → 0.712 → 0.894로 올랐고, 수정에 쓰지 않은 검증 12문항은 0.917이었다.
<sub>같은 코드도 한 번 돌릴 때마다 ±0.06 흔들려서(seed를 고정해도 GPU 비결정성) 여러 번 돌린 평균으로만 판단했다. 원문 표에 체크리스트 식별자가 그대로 들어가 점수가 오르는 면이 있다는 것도 문서에 적었다.</sub>

**5. holdout을 보고 고치면, 그 문항은 holdout이 아니다.**
holdout 결과를 보고 코드를 고친 문항은 dev로 옮기고 새 holdout을 만들었다. 내가 만든 문항은 시스템을 알고 쓴 것이라 낙관적이어서, 다른 사람이 작성한 독립 평가셋도 받아 따로 쟀다.
<sub>Profile M: dev 28문항 0.954, holdout 12문항 0.945. 독립 평가셋 I 9문항 1.0, J 6문항 0.778.</sub>

**6. 실제 질문 3개가 자체 평가보다 많은 걸 잡았다.**
실제 사용 질문 3개에서 판정 버그 4개가 나왔고, 자체 평가 문항은 그중 하나도 잡지 못했다. 그래서 표현만 바꾼 35문항(고칠 때 쓰는 것)과 새 20문항(과적합 확인용, **이 결과로는 고치지 않는 것**)을 따로 만들었다.
<sub>35문항 33/35, 새 20문항 16/20. 새 20문항의 실패 4개 중 3개는 조건을 단어 목록으로 뽑는 방식이 새 표현을 놓친 것이었다.</sub>

**7. 7B가 지어낸 이름은 원문 대조로 걸렀다.**
7B는 그럴듯한 토픽 이름을 지어냈다. 원문에 정의되지 않은 tns1·tt 이름이 들어간 문장을 지우고, XSD 구조와 다른 소속 주장도 지웠다. 지어낸 이름은 응답당 0이 됐다.
<sub>못 잡는 것: 이름은 맞는데 관계가 틀린 주장. 자동 점검은 화면에 보이는 모델 작성분에만 적용한다(내 코드가 쓴 원문 표에 경고가 붙던 문제를 겪고 나서).</sub>

**8. 증명하지 못한 것.**
팀 실사용 검증 전에 개발을 마쳤다. 질문에 ONVIF 식별자가 없으면 76문항 중 13문항이 다른 기능의 원문으로 갔다. 원문 블록은 글자는 정확하지만 질문에 맞는 원문인지는 보장하지 않는다. 그래서 화면과 문서 맨 위에 "답이 틀릴 수 있다"는 경고를 먼저 붙였다.
<sub>Profile 대조 정답 후보 34건은 사람 검토 전(0/34). 영어 질문은 점검 6문항 중 3문항의 경로가 틀렸다. "찾지 못함"은 검색된 근거에 없다는 뜻이지 ONVIF에 없다는 뜻이 아니다.</sub>
