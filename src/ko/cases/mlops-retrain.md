# 설치 환경이 제각각인 카메라를 자동 재학습으로 따라가기

**정원석** | 2026.02~05 · 온디바이스 검출기를 탑재한 상용 AI 카메라 + 로컬 GPU 서버 · 클라우드 미사용

<sub>담당: 파이프라인 전 구간 설계·구현 (수집 · 자동 라벨링 · 클러스터링 · 학습 · 양자화와 변환 · 배포 · 평가). 관리 화면 프론트엔드는 타 담당.</sub>

> 카메라가 설치된 환경에 맞춰 검출 모델을 사람 개입 없이 다시 학습시키고 배포할 수 있는지 만들어 본 기록.
> **만든 결과가 아니라 구조를 네 번 갈아엎은 이유**이고, 아래 여덟 개 중 다섯이 실패이거나 끝내 확인하지 못한 것이다.

---

**1. 같은 가중치인데 현장마다 다르게 틀렸다.**
어떤 곳은 그림자를, 어떤 곳은 특정 구조물을 사람으로 잡았다. 공용 가중치 하나를 잘 만드는 것으로는 닿지 않는 문제라고 봤다.
<sub>제약 네 가지: 최대 100대 동시 관리(목표치) · 월 또는 계절 주기 · 로컬 서버이고 데이터를 클라우드로 내보내지 않음 · 사람이 라벨을 붙지 않음.</sub>

**2. 목표 지표가 중간에 반대로 뒤집혔다.**
처음에는 미탐을 조금 허용하더라도 오탐을 줄이는 쪽이었는데, 고객 의견이 들어오면서 정반대가 됐다. 임계값을 코드에 박아두지 않고 사이클마다 따로 저장하게 만든 것은 이 전환을 겪고 나서다.
<sub>설계 시점의 목표가 바뀔 수 있다는 것을 전제에 넣지 않았던 결과다.</sub>

**3. 구조를 네 번 갈아엎었다.**
파일 이름으로 데이터를 관리하던 프로토타입은 2대째부터 성립하지 않았다. DB 상태 기반으로 다시 짜면서 데이터 하나의 진행을 컬럼 하나가 지배하게 하고 12개 상태를 정의했다.
<sub>v0.1 직렬 → v1.0 상태 기반 병렬 → v1.1 클러스터 단위 학습(카메라마다 학습하니 GPU가 모자랐다) → v2.0 배포 후 평가. 워커는 자기 상태만 집어가고, 집는 순간 진행 중으로 바꿔 중복 처리를 막는다.</sub>

**4. 갇힌 데이터를 살리는 작업이 더 나쁜 일을 만들 뻔했다.**
진행 중 상태에서 워커가 죽으면 그 데이터는 아무도 집어가지 않는다. 10분마다 되돌리게 했는데, 무조건 돌리면 살아서 처리 중인 워커의 데이터까지 뺏어와 같은 데이터를 두 번 처리한다. **그 상태를 담당하는 서버가 전부 죽어 있을 때만** 되돌리도록 조건을 걸었다.
<sub>복구를 늦게 하는 것이 중복 처리보다 낫다고 판단했다.</sub>

**5. 모델이 만든 라벨을 믿지 않았는데, 검증하는 쪽은 검증하지 않았다.**
검출 모델이 후보 라벨을 만들고 VLM이 객체마다 맞는지 판정해 틀린 것을 버리는 2단계로 나눴다. 그런데 **그 VLM의 판정이 맞는지는 누구도 확인하지 않았다.** 표본을 떼어 사람이 대조하는 절차를 넣었어야 했다.
<sub>5종(사람·차량·이륜차·번호판·얼굴). 이미지를 통째로 판정하면 한 객체 때문에 멀쩡한 라벨까지 버리게 되어 객체별 판정으로 설계. 자동 라벨의 신뢰도는 지금도 모른다.</sub>

**6. 몇 개로 묶을지를 거리로 정하지 않았다.**
카메라 100대에 모델 100개는 학습도 배포도 관리도 감당이 안 되어 비슷한 환경끼리 묶었다. 임계값을 특징 공간의 거리로 정할 수도 있었지만, **후보 4개마다 실제로 작은 모델을 학습시켜 F1과 mAP로 골랐다.** 묶는 목적이 특징이 가까운 것이 아니라 같이 학습시켰을 때 잘 되는 것이기 때문이다.
<sub>카메라당 24시간에 걸쳐 96장 수집 → 특징 추출 후 낮과 밤을 나눠 따로 인코딩해 이어 붙임. 섞어서 평균 내면 어느 쪽도 아닌 벡터가 된다. 학습 비용은 사이클당 한 번이라 감당 가능하다고 봤다.</sub>

**7. 지표가 이상했는데 모델 문제가 아니었다.**
번호판과 얼굴의 미탐률이 비현실적으로 높게 나왔다. **카메라 펌웨어가 그 두 클래스를 애초에 내보내지 않고 있었다.** 집계에서 뺐지만 지우지 않고 설정 토글로 남겨, 펌웨어가 고쳐지면 과거에 쌓인 것까지 소급해 반영되게 했다.
<sub>온디바이스 검출 결과와 검증된 라벨을 IoU 0.5로 매칭해 클래스별 FPR·FNR 집계. 배포가 카메라마다 순차로 이뤄져 카메라별 배포 시각으로 평가 윈도우를 끊었다.</sub>

**8. 배포까지 자동으로 돌았고, 나아졌는지는 끝내 재지 못했다.**
학습된 모델은 INT8 QAT를 거쳐 카메라 SoC 바이너리로 변환돼 실제로 올라갔다. **변환 전후의 정확도 차이도, 재학습의 개선 폭도 측정하기 전에 중단됐다(2026.05).** 묶어서 학습하는 것이 개별 학습보다 이득이었는지도 모른 채 끝났다.
<sub>이 기록에 "오탐이 몇 % 줄었다"는 문장이 없는 이유다. 기능을 먼저 쌓고 효과 측정을 v2.0에 붙인 것이 순서 착오였고, 평가 스테이지는 v0.1에 있었어야 했다.</sub>
